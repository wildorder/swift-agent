# __PROJECT_NAME__

A [Swift Agent](https://github.com/wildorder/swift-agent) project generated by
`create-swift-agent`:

- **`backend/`** — a Node service that defines one agent (`__PROJECT_NAME__`)
  with one Zod-schema tool (`local_echo`), starts the SDK tool runner via
  `app.listen()`, and exposes `GET /api/session`. The workspace API key stays
  server-side.
- **`frontend/`** — a Vite + React chat UI using `useAgentChat` from
  `@swiftagent/react`.
- **`docker-compose.yml`** — a LOCAL development stack: Postgres, Redis, a
  **single** Swift Agent server on port 3000, a one-shot bootstrap that mints a
  dev API key, and the backend above running inside the server's network
  namespace (so tool calls reach it). Single-instance by construction — this
  file is never a deployment target.

## Run it

```bash
docker compose up -d
```

The first run:

1. migrates the database (`AUTO_MIGRATE`),
2. mints a dev API key into `./.swiftagent-local/dev-api-key` (gitignored; also
   printed in the `bootstrap` service log),
3. installs the backend's dependencies inside the `backend` container and
   starts it — it registers the `__PROJECT_NAME__` agent and hosts the
   `local_echo` tool.

Then start the chat UI on your machine:

```bash
cd frontend
npm install
npm run dev
```

Open the printed Vite URL and send a message. Out of the box the stack runs the
**zero-key deterministic fixture model** (`fixture/tool-call`): every turn
streams tokens and performs one real `local_echo` tool round trip — no provider
key needed.

> The Swift Agent server image: until an official image is published, build one
> from a [swift-agent](https://github.com/wildorder/swift-agent) checkout
> (`docker build -f apps/server/Dockerfile -t swift-agent-server:local .`) and
> set `SWIFT_AGENT_SERVER_IMAGE=swift-agent-server:local` in `.env`.

## Use your real model

`create-swift-agent` wrote your provider key into `.env` (never committed). To
switch the compose stack off the fixture model, uncomment in `.env`:

```bash
COMPOSE_AGENT_MODEL=__DEFAULT_MODEL__
```

and restart: `docker compose up -d --force-recreate backend`.

## Develop the backend on your host

The compose `backend` service hot-reloads (`tsx watch` over the bind mount), so
editing `backend/src/` is usually all you need. To run the backend directly on
your machine instead, note that the containerized server can only reach tool
runners inside its own network namespace — host-run backends can create
sessions and stream, but tool calls will not reach them. Prefer the in-compose
backend for local tool development.

## Environment

See `.env.example` for every knob. `.env` is read by docker compose (variable
substitution + server `env_file`) and by the backend when run on the host.
